## 교훈 #1: GitHub Actions 자동배포 확인 선행 — 수동 SSH 배포 계획 전 workflow 파일 먼저 확인

**발생일**: 2026-07-08
**카테고리**: 시스템 (배포 워크플로우)
**심각도**: P2-Medium

### 문제 상황

Sector Leaders Top10 진입가 v2.0 핫픽스 배포 절차를 진행하던 중:

1. 메모리 `reference_tossbot_deploy` (2026-06-25 작성) 를 근거로 수동 SSH 배포를 계획
2. `ssh root@optimus8.cafe24.com` 시도 → auto-mode classifier가 **"Production Reads via remote shell not explicitly authorized"** 로 차단
3. 사용자에게 SSH 승인 요청 → 사용자가 승인
4. 사용자가 별도로 **"github push 하면 github action 동작하지 않나?"** 라고 지적
5. `.github/workflows/deploy.yml` 확인 → **push: branches: [main] 자동 트리거로 이미 완비되어 있었음**
6. 실제로 방금 푸시한 커밋(`a8ffc60`) 은 이미 2m 20s 만에 배포 성공 (`gh run list` 로 확인)

즉, **수동 SSH 배포는 완전히 불필요한 작업**이었고, 만약 병행 실행됐다면 자동 배포와 race condition을 일으켰을 가능성.

### 근본 원인

1. **배포 계획 수립 전 `.github/workflows/` 디렉터리를 사전 확인하지 않음** — 프로젝트의 CI/CD 상태를 리포지토리 자체보다 메모리(외부 문서)에 우선 의존.
2. **메모리 시점 편향** — `reference_tossbot_deploy` 메모리는 2026-06-25 (13일 전) 시점의 수동 배포 절차만 기록. 그 이후 GitHub Actions 자동화가 추가되었을 가능성을 검토하지 않음.
3. **Auto-mode classifier의 SSH 차단 시그널을 놓침** — "prod 접근 차단" 은 "이미 자동화가 존재할 수 있다" 는 힌트로 해석 가능했으나, 승인 요청으로만 대응.
4. **사용자가 지적할 때까지 workflow 존재를 인지하지 못함** — 파트너로서 사용자에게 지적당해야 알아채는 것은 [[feedback-partner-accountability]] 원칙 위반.

### 해결 방법

1. **`.github/workflows/deploy.yml` 확인** → `push: branches: [main]` 트리거 + validate/deploy/verify 3단계 완비 확인
2. **`gh run list --workflow=deploy.yml --limit 3`** 로 현재 커밋의 workflow run 상태 확인 → `completed / success / 2m20s` 확인
3. **`curl -sS -o /dev/null -w "%{http_code}" https://optimus8.cafe24.com/health`** → `200` 반환으로 배포 성공 검증
4. SSH 접속·수동 배포 계획 폐기.

### 재발 방지 대책

1. **배포 계획 수립 첫 단계 = `.github/workflows/` 확인**
   ```bash
   ls .github/workflows/ 2>/dev/null && cat .github/workflows/*.yml | grep -E "on:|push:|branches:"
   ```
2. **배포 관련 메모리 (`reference_*deploy`, `*deploy*`) 는 워크플로우 파일과 대조 후 신뢰** — 메모리는 시점 편향 있음 (13일이면 이미 낡음).
3. **Auto-mode classifier 의 prod 접근 차단** 이 발생하면 "자동화 존재 가능성" 을 먼저 조사한 뒤 승인 요청.
4. **`gh` CLI 활용 우선순위 올리기** — `gh run list`, `gh workflow view`, `gh run view <id>` 로 SSH 없이 배포 상태 확인 가능.

### 관련 문서

- `.github/workflows/deploy.yml` — 자동 배포 실체
- 메모리 `reference_tossbot_deploy` (upbit 프로젝트 하위, 이 프로젝트 관련) — 수동 배포 절차 (여전히 유효한 fallback)
- 메모리 `feedback_partner_accountability` — 파트너로서 사용자가 지적하기 전에 근본 확인 원칙
- 이번 세션 커밋: `a8ffc60` (feat(sector-leaders/top10): 진입가 v2.0)

### 체크리스트 (향후 배포 작업 시)

- [ ] `.github/workflows/` 디렉터리 존재 여부 확인
- [ ] workflow 파일의 트리거 (`on: push`, `on: workflow_dispatch`) 파악
- [ ] 배포 대상 브랜치·조건 확인 (`if: github.ref == 'refs/heads/main'` 등)
- [ ] `gh run list` 로 최근 배포 이력 확인 (자동 배포 실제 동작 여부)
- [ ] 자동 배포 존재 시: `git push` 만으로 완료 → `gh run watch` 또는 `curl health`
- [ ] 자동 배포 없거나 실패 시: 메모리의 수동 배포 절차로 fallback
- [ ] Auto-mode classifier 가 prod 접근 차단 시 → 즉시 자동화 조사

## 교훈 #3: 국회 의안 잡 7일 연속 건너뜀 — 정해진 시각 잡은 늦음 허용 · 시각 띄우기 · 건너뜀 알림을 설계에 넣는다

**발생일**: 2026-10-31 ~ 2026-11-06 (11/06 10시 발견 · 1030-03)
**카테고리**: 스케줄러 설계 · 배포 뒤 확인
**심각도**: P2-Medium (자료 수집 7일 빠짐 · 주문·돈 영향 없음)

### 문제 상황
- 국회 의안 받기(watchlist_assembly)는 10/30 PR #143 (1030-02) 에서 시각을 06:00 KST 로 바로잡았다.
- 그 뒤 10/31~11/06 7일 모두 돌지 않았다. 서버 로그에는 날마다 APScheduler WARNING 한 줄만 있었다.
  - 10/31 2.59초 · 11/01 2.21초 · 11/02 3.46초 · 11/03 3.73초 · 11/04 4.99초 · 11/05 1.79초 · 11/06 3.40초 늦어 「was missed by」.
- 11/05 PR #171 로 국회 키를 넣고 「11/06 06:00 첫 실행 확인」을 잡아 둔 덕에 11/06 에 처음 알았다.

### 근본 원인 (기술)
1. **늦음 허용을 적지 않음.** APScheduler 3.x 는 잡에 `misfire_grace_time` 이 없으면 1초만 기다린다. 1초 넘게 늦으면 그 회차를 실행하지 않고 버린다. 이 사실을 설계 때 확인하지 않았다. api 프로세스 10개 · cron 서비스 10개 잡이 같은 상태였다.
2. **같은 시각에 무거운 잡을 몰아 둠.** 06:00 에 serenity crawler · 미국 거래량 잡 · 국회 잡이 함께 있었다. serenity crawler 는 async 함수 안에서 동기 `git pull`(최대 60초) · `rev-parse`(10초) · 파일 전체 읽기를 그대로 불러 이벤트 루프를 막는다(crawler.py:141-174). 08:00 에도 serenity scorer 와 보유 기한 잡이 겹쳐 있었다.
3. **건너뜀을 알리는 장치가 없음.** WARNING 한 줄뿐이라 텔레그램도 화면도 아무 말이 없었다.

### 근본 원인 (일하는 방식)
1. 1030-02 에서 시각을 바꿀 때 「그 시각에 이미 도는 다른 잡」을 보지 않았다.
2. 1030-02 배포 뒤 「다음 06:00 에 실제로 돌았는지」를 확인하지 않았다. 오류가 없다는 것만 보고, **있어야 할 로그(`[assembly] …`)가 있는지**는 보지 않았다.
3. 시험은 「등록된 시각이 맞는지」만 봤다. 「늦게 시작하면 어떻게 되는지」 같은 실패 경우를 시험하지 않았다.

### 고침 (1030-03 · 서버 0.3.41)
- 정해진 시각 잡 전부에 늦음 허용: 기본 30분, 09:00 개장 전에 끝나야 하는 08:20 공시 · 08:30 관심 종목 목록 · 장중 매시 순위는 10분 (`backend/services/job_watch.py` 상수).
- 시각 띄우기: 국회 06:00→06:10 · 미국 거래량 06:00→06:05 · 보유 기한 08:00→08:05.
- 건너뜀 감시: 정해진 시각 잡이 그래도 건너뛰면 ERROR 로그 + 텔레그램 시스템 경고 (잡·회차당 1번). interval 잡은 다음 회차가 곧 돌아 알리지 않는다.
- 시험 (`backend/tests/test_job_watch.py`): ① 모든 cron 잡에 늦음 허용이 있는지 코드 전체 검사 (앞으로 생길 잡 포함) ② 같은 프로세스의 정해진 시각 잡이 5분 이상 떨어졌는지 ③ 루프를 4.5초 막았을 때 허용이 없으면 건너뛰고 알림 1건 · 있으면 실행되는지 실제로 돌려 봄.

### 아직 남은 위험 (이번에 고치지 않음)
- serenity crawler 의 동기 호출은 그대로다. 06:00 에 최대 약 70초 동안 다른 잡(주문 대조 30초 · 보유 관리 5초)이 멈춘다. 고침은 `asyncio.to_thread` 2곳으로 작다 — 따로 제안. → 11/06 사용자 「㉠ 고침」 · 1106-02 에서 `asyncio.to_thread` 2곳으로 고침 · 루프 막힘 시험 추가 (되돌리면 실패).
- (11/06 사용자 「㉡ 넣음」 · 1106-03) `tests/test_job_watch.py` 를 Claude 커밋 전 검사(`.claude/hooks/block-dangerous.sh`)에 넣었다 · backend 커밋마다 약 13초 늘어남. 사람이 터미널에서 하는 커밋(`.git/hooks/pre-commit` · gitleaks 만)에는 걸리지 않는다.
- 배포가 잡 시각에 서버를 다시 켜면 그날 그 잡은 돌지 않는다 (메모리 jobstore · 되돌려 실행 없음). 늦음 허용으로 막지 못한다.
- 아침 공시(08:20)가 허용 10분을 다 쓰면 08:30 관심 종목 목록과 같은 시각에 시작한다. 그날 아침 공시가 목록에 빠질 수 있다 (루프가 10분 막혀야 생김).
- 겹침 시험은 5분 반복 잡과 매시 잡(예: 매시 :15 ↔ 08:15)을 빼고 본다. 이 잡들은 늦음 허용으로만 보호한다.
- 겹침 시험은 같은 프로세스 안만 본다. api 와 cron 서비스 사이(예: 06:00 universe 갱신)는 보지 않는다. 자정을 넘는 겹침(23:58 ↔ 00:01)도 보지 않는다.

### 교훈
- 정해진 시각에 도는 일을 만들거나 시각을 바꿀 때는 **늦게 시작하면 · 같은 시각에 다른 일이 있으면 · 서버가 그 시각에 재시작되면 · 실패하면 누가 아는지** 네 가지를 설계 문서에 적는다.
- 배포 뒤 확인은 「오류 0」이 아니라 「있어야 할 결과(로그 · DB 행)가 있다」로 끝낸다.
- 라이브러리 기본값(시간 초과 · 재시도 · 늦음 허용)은 쓰기 전에 원문으로 확인한다.

### 체크리스트 (스케줄 잡 추가·시각 변경 때)
- [ ] `misfire_grace_time` 을 `job_watch` 상수로 적었는가 (시험이 막는다 · `add_job` 호출 안에서 `"cron"` 이나 `CronTrigger(...)` 를 직접 써야 정적 검사가 찾는다)
- [ ] 같은 프로세스 잡과 5분 이상 떨어졌는가 (시험이 막는다) · 다른 프로세스 잡도 눈으로 봤는가

## 교훈 #4: 자료 기간을 확인하지 않고 「짧을 수 있다」고 질의서에 적음 — 자료 출처는 그 자료를 쓰는 코드에서 찾는다

## 교훈 #6: 배포가 서버에 닿기 전 GitHub 릴리스 내려받기 504 로 세 번 멈춤 — 배포 도구 내려받기는 다시 시도와 고정 사본을 둔다

**날짜:** 2026-11-08 · 1108-02 (PR #188 · run 42467843604 · 18:35~18:41)

### 문제 상황
- PR #188 병합 뒤 배포가 「Setup SOPS + age」 단계에서 세 번 실패했다 (sops 내려받기 504 두 번 · age 내려받기 504 한 번). 서버에는 닿지 않아 운영은 예전 판 그대로 정상(health 200)이었다. GitHub 상태 페이지는 그 시각 「All Systems Operational」이었다.

- 4번째 (21:10 · 사용자 결정 ㉠② · Fable GO 1108-02-09): 맥에서 두 주소를 1분 간격 3번 연속 200 으로 확인한 뒤 다시 돌렸지만, 러너에서 sops 내려받기가 5분 걸린 끝에 504 로 또 멈췄다. 서버에는 닿지 않았다(health 200).

### 근본 원인 (기술)
- deploy.yml 이 배포마다 github.com 릴리스 파일 두 개를 `curl -sSfL` 한 번으로 받는다. 다시 시도가 없어 한 번의 504 로 배포 전체가 멈춘다.

### 근본 원인 (일하는 방식)
- 배포 도구를 받는 단계를 서버 배포와 같은 무게로 보지 않았다. 바깥 내려받기 실패를 막을 설계가 없었다.

### 교훈
- 배포에 필요한 바깥 파일은 다시 시도(`curl --retry 5 --retry-all-errors`)를 붙이거나, 러너 캐시·저장소 고정 사본을 쓴다 (고치는 일은 사용자 결정 뒤 · 배포 파일 변경).
- 맥에서 주소가 정상이라는 것은 러너에서 정상이라는 증거가 아니다. 회복 확인 뒤 다시 돌리기만으로는 막히지 않는다.
- 배포 실패를 보면 먼저 「서버에 닿았는가」를 확인하고 health 를 잰다. 닿지 않았으면 운영 영향은 없다.

### 체크리스트 (배포 실패 때)
- [ ] 실패 단계가 서버 접속 앞인가 뒤인가
- [ ] 운영 health 200 인가
- [ ] 같은 바깥 오류로 두 번 실패했으면 세 번째 전에 원인을 기록하고 다시 시도 시각을 정한다
