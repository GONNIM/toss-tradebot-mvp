## 1. 지킬 것

1. 실거래 스위치는 관리자 화면에서만 켠다. 켜기는 쿠키 로그인 + Origin 검사 + 텔레그램 확인 코드. 코드 · 스크립트 · 마이그레이션 · 시험은 스위치 파일에 켜짐을 쓰지 않는다(시험이 막는다).
2. 실거래 스위치는 기존 `SNIPER_LIVE_ENABLED` · `order_target` · 스나이퍼 `enabled` 와 독립이다. 계획 실행기를 켜도 스나이퍼는 켜지지 않는다.
3. 꺼져 있으면 실전 계획은 APPROVED 에서 멈추고 「실거래 꺼짐 · 새 주문 안 냄」을 보인다. 실전 계획을 모의로 대신 돌리지 않는다.
4. Kill Switch 는 기존 뜻 그대로: 새 진입 멈춤 → 계획 매수 금지 · 대기 매수 취소 · 매도 다리 유지 / 매도도 멈춤 → 계획의 모든 조건주문 취소 · HALTED.
5. 공개 저장소: 시험은 가상 종목(`TEST1`…)과 가상 가격. `.gitignore` 는 바꾸지 않는다.
6. 토스 토큰은 설정 키 `TOSS_TOKEN_ISSUE=1` 이 있는 곳(운영 서버 · SOPS 에만 둠)에서만 새로 발급한다(9-1). 실행기와 웹소켓도 같은 키가 있을 때만 시작한다. 키가 없으면 시작하지 않고 로그 1줄만 남긴다. `APP_ENV` 는 운영 서버에 없으므로(11/16 서버 확인) 판단에 쓰지 않는다. 로컬 서버 기동은 막지 않는다(`BIOTECH_API_ONLY=1 TELEGRAM_BOT_TOKEN=` 규칙 유지). 로컬 시험은 가짜 토스 클라이언트만.
7. 비밀값은 로그 · 알림 · 오류에 남기지 않는다. 계좌는 끝 4자리만. 확인 코드는 저장할 때 해시만 둔다.
8. 정해진 시각 작업은 `misfire_grace_time` · 같은 프로세스 5분 간격 · 건너뜀 알림을 갖춘다(교훈 #3 · `tests/test_job_watch.py`). 배포 금지 시간대를 지킨다.
9. 모의(paper)는 시험 전용이다. 모의 계획은 토스 주문 · 조건주문 API 를 부르지 않는다(시험이 막는다). 시세만 읽고 체결은 가상. 가상 보유 · 주문은 별도 표. 실제 계좌 보유 · 조건주문을 상태 판단에 쓰지 않는다.

## 3. 인증

| 동작 | 받는 인증 | Origin 검사 |
|---|---|---|
| 조회(목록 · 상세 · 다리 · 이벤트 · 불변식 · 실행기 상태) | 관리자(쿠키 · 헤더) | 없음 |
| 새 계획 · 초안 수정(DRAFT 만 · 그 밖의 상태는 값 수정 거부) | 관리자(쿠키 · 헤더) | 있음(쿠키일 때) |
| 확인 코드 요청(실거래 켜기 · 승인 · 인수 · 재개) | **쿠키만** | 있음 |
| 인수 취소 · 시간 손절 중지 | 쿠키 · 헤더 모두(위험을 줄이는 동작) | 쿠키일 때 있음 |
| 실전 · 실제 주문 시험 계획 승인 · 보유 인수 · 그 계획의 HALTED 재개 | **쿠키만** + 텔레그램 확인 코드(4-2-1) | 있음 |
| 모의 계획 승인 · 모의 계획 HALTED 재개 | **쿠키만** | 있음 |
| 계획 정지 | 쿠키 · 헤더 모두 | 쿠키일 때 있음 |
| 스위치 끄기 · 모의 스위치 켜기 | **쿠키만** | 있음 |
| 실거래 스위치 켜기 | **쿠키만** + 텔레그램 확인 코드 | 있음 |

- 쿠키 전용 의존성은 새 인증이 아니다. 기존 관리자 확인(`api/auth.py` `_pick_token` 의 출처 구분)을 그대로 쓰고 출처가 `cookie` 일 때만 통과시킨다. 헤더면 403.
- Origin 검사: `Origin`(없으면 `Referer`)이 운영 주소와 같아야 한다. 없거나 다르면 403. 로컬은 허용 목록에 로컬 주소.
- 로그아웃 상태는 모든 계획 API 가 401. 운영 curl 로 확인하는 것이 완료 기준이다.
- 모든 성공 · 실패는 기존 접속 기록(`sniper_api_access`)에 남긴다.
- 「계획 정지」(헤더 허용)의 뜻 (Fable 권고 2): 그 계획의 새 등록 · 매수를 멈추고 대기 매수를 취소한다. **매도 다리는 지우지 않는다.** 다리를 지우는 것은 Kill Switch 「매도도 멈춤」뿐이다.
- 막음 4 (Fable) → 사용자 결정 ㉤ ① (11/16): 쿠키 값 = 관리자 토큰이라 「쿠키만 + Origin」은 토큰을 가진 쪽이 헤더를 꾸미면 통과하고, 대표 브라우저를 쓰는 Aside 도 통과한다. 그래서 실전 · 실제 주문 시험 계획 승인 · 보유 인수 · 그 계획의 HALTED 재개에 텔레그램 확인 코드를 더한다(4-2-1). 코드는 대표 휴대폰에만 오므로 토큰을 가진 쪽과 Aside 모두 혼자서는 통과하지 못한다. 모의 계획은 결정 3 대로 코드 없이 Aside 도 승인한다. 쿠키 자체를 고치는 일은 1116-02 로 그대로 둔다.
- 계획 승인 주체 칸: 실전 · 실제 주문 시험 계획 = 대표(쿠키 로그인). 모의 계획 = 대표 또는 「Aside(대표 지시)」. 실전 · 시험 계획 승인 화면에서는 Aside 표시를 고를 수 없다.

## 4. 스위치

### 4-1. 두 스위치
| 스위치 | 처음 값 | 켜기 | 끄기 |
|---|---|---|---|
| 실거래 주문 | 꺼짐 | 쿠키 + Origin + 확인 코드 + 까닭 | 쿠키 + Origin · 한 번 누름 |
| 모의 시험 | 꺼짐 | 쿠키 + Origin + 까닭 | 쿠키 + Origin · 한 번 누름 |

### 4-2. 실거래 켜기 확인 코드
1. 화면 「켜기」 → `POST /api/v1/plans/switches/live/challenge` → 서버가 6자리 숫자(`secrets`)를 만들고 해시 · 만든 시각 · 5분 만료 · 시도 0 을 저장, 텔레그램 「⑨ 실주문」 범주로 즉시 보냄(하루 요약 모드여도 즉시 · 코드는 알림 기록 화면에 남기지 않음).
2. 화면에 코드 입력 → `POST /api/v1/plans/switches/live {on: true, challenge_id, code, reason}` → 맞으면 켬 · 코드 즉시 무효.
3. 막는 것: 5분 지나면 무효 · 한 코드 5번 틀리면 무효 · 15분에 코드 요청 3번까지 · 새 코드를 만들면 옛 코드 무효 · 하루(KST) 실패 누적 10번이면 다음 날까지 켜기 잠금 · 실패마다 ⑨ 알림 (Fable 권고 1).
3-1. 저장은 서버 비밀값(SOPS 새 키)으로 만든 HMAC-SHA256 만 두고, 비교는 `hmac.compare_digest`(상수 시간).
4. 텔레그램 토큰이 없으면(로컬) 코드를 보낼 수 없어 켤 수 없다.

### 4-2-1. 같은 확인 코드를 승인 · 인수 · 재개에도 (결정 12 · ㉤ ①)
- 대상: 실전 · 실제 주문 시험 계획 승인, 보유 인수 승인, 그 계획의 HALTED 재개. 모의 계획 · 계획 정지 · 인수 취소 · 스위치 끄기는 코드 없음(위험을 줄이는 동작이거나 결정 3).
- 요청: `POST /api/v1/plans/confirm/challenge {action, plan_id}` → 4-2 와 같은 6자리 · 5분 · 즉시 발송. 알림 문구에 동작 이름과 계획 번호를 넣는다(종목 · 금액은 넣지 않음).

## 5. 수량과 매도 예약 장부 (결정 5)

1. 계획 보유 `plan_qty` = 이 계획 매수 체결 합 − 이 계획 매도 체결 합(이 계획의 주문 번호 · 고유 키로만 셈). 인수 계획은 인수 수량에서 시작.
2. 다리 기준 수량 `base` = min(`plan_qty`, 계좌 보유). 계좌 보유가 더 적으면 알림 + 다리 축소.
3. 계획 밖 보유는 「계획 밖 보유 n주(실행기가 팔지 않음)」로 보이고 건드리지 않는다.
4. **접수된 매도 수량** `accepted_sell` = 토스에 실제 접수된 매도 주문의 남은 수량 합: 발동된 조건주문 · TP1 감시 모드 지정가 · 시간 손절 지정가. 발동 전 TP1 조건주문은 넣지 않는다. 「시간 손절 지정가」는 7-4 의 발동된 다리를 취소하고 다시 낸 지정가를 뜻한다(따로 새로 내는 매도는 없음). 취소하고 다시 내는 동안에도 그 수량은 장부에 예약으로 남겨, 모자람 규칙이 다리를 한 번 더 걸지 않게 한다(Fable 2차 권고 2).
5. **불변식 A:** 대기 중(WATCHING) 손절 다리 수량 합 = `base` − `accepted_sell`.
6. **불변식 B:** TP1 조건주문(등록 모드) 수량 ≤ `base` − `accepted_sell` 의 ½ 내림. 이 합이 보유를 넘는 등록이 거절되면(U1) TP1 감시 모드.
6-1. **불변식 C (Fable 막음 3):** 계좌 보유 > `plan_qty`(계획 밖 보유가 있음)이면 TP1 등록 모드를 쓰지 않고 TP1 감시 모드로 강제한다. 계획의 매도 조건주문 합(TP1 포함)이 계획 밖 보유를 침범하는 순간이 없게 한다.
6-2. 같은 종목에 열린 계획은 1개만(새 계획 · 인수 모두 · Fable 권고 4).
7. 계획 매도 주문(TP1 감시 · 시간 손절)을 내기 **전에** 손절 다리를 그만큼 줄인다. 그 매도를 취소하면 원래대로.
8. 매수 주문은 계획당 동시에 1개.
9. 사다리 수량 = `base` − `accepted_sell` 을 3 으로 나눠 내림, 나머지는 마지막 단계.
10. 체결 · 전이 · 다시 맞추기 직후 불변식 검사 (Fable 막음 2):
   - **모자람**(손절 합 < `base` − `accepted_sell`): 닫힌 조건주문(발동 · 체결 이력)과 체결을 먼저 다시 읽어 `base`·`accepted_sell` 을 고친 뒤, 그래도 모자라면 모자란 수량만큼 보호 다리를 다시 건다. HALTED 상태에서도 이 「보호 다리 다시 걸기」는 허용한다. ⑨ 알림.
   - **넘침**(손절 합 > 기준) 또는 짝이 여럿: 새 등록을 멈추고 HALTED + ⑨ 긴급. 넘친 다리 축소(수량 줄이기 · 취소)는 HALTED 에서도 한다.
   - 정상 넘침 (Fable 2차 권고 3): TP1 · 손절 다리가 발동해 `accepted_sell` 이 늘어난 직후 다른 다리를 줄이는 것은 정상 처리다. 이때는 넘침으로 보지 않고 바로 줄인다. 줄이기가 3번 실패할 때만 넘침으로 본다.
   - 다시 거는 보호 다리의 값 · HALTED 중 시간대 교대 (권고 4): 다시 거는 다리는 그때 시간대 값(7-1)으로 건다. HALTED 에서도 시간대 교대 수정은 한다(보호를 지키는 동작).
   - HALTED 에서 허용: 보호 다리 다시 걸기 · 넘친 다리 줄이기 · 시간대 교대 수정 · 다시 맞추기. 금지: 매수 · 다리 위로 올리기 · TP1 · 시간 손절.

## 7. 계획 값 · 다리

v4 4~5절 그대로 + 아래 고침.

### 7-1. 시간대 다리
- 장 시간은 `GET /api/v1/market-calendar/US` 를 매일 읽는다(기존 `execution/market_calendar.py`).
- 아래쪽 다리는 늘 SINGLE SELL 3건. 시간대가 바뀌면 같은 3건을 **수정**(토스는 취소 뒤 새 번호 · WATCHING·PAUSED 만).
- 정규장: 사다리 · 주문가 = 감시가 × 0.98 / 정규장 밖(데이 · 프리 · 애프터): 3건 모두 비상 손절 −15% · 주문가 × 0.97.
- 전환 시각: 정규장 시작 1분 뒤 · 종료 1분 뒤.
- 수정 실패: 3초 뒤 다시 조회 · 다시, 3번 실패면 HALTED + 알림. 수정 실패 뒤 옛 주문이 남는지는 확인되지 않았다(U7 · 소액 시험). 다시 조회했을 때 옛 주문도 새 주문도 없으면 5절 10항 「모자람」으로 즉시 보호 다리를 다시 건다.

### 7-2. 수정 중 기록 (남은 문제 6)
- 수정 전에 `plan_leg_pending`(옛 번호 · 바꿀 감시가 · 주문가 · 수량 · 시각)을 쓴다.
- 응답으로 새 번호를 받으면 다리에 저장하고 기록을 지운다.
- 다시 맞출 때 기록이 남아 있으면 (Fable 답 4):
  1. 1순위 열쇠 `clientOrderId` 로 찾는다(U6 로 이어짐이 확인되면).
  2. 없으면 같은 종목 · 매도 · 수량 · 감시가 · 주문가인 OPEN 조건주문 가운데 **이미 다른 다리에 이어진 번호를 뺀** 후보에서 찾는다.
  3. 후보 1개면 잇는다. 옛 번호만 살아 있으면 옛 값으로 두고 수정을 다시 시도한다(틀린 시간대 값이 남지 않게).
  4. 후보가 여럿이면 넘침으로 보고 HALTED. 옛 · 새 모두 없으면 모자람으로 보고 보호 다리를 다시 건다(5절 10항).
- 수정 뒤 주문 고유 키가 이어지는지는 U6 으로 소액 시험에서 확인.

### 7-3. 익절 뒤 (남은 문제 1 · 2)
- TP1 체결 → 추적 감시가 = max(평단, 정규장 고점 × 0.85) 를 계산.
- 감시가 < 현재가이면 추적 전환 (Fable 막음 3 고침): **추적 손절도 3건을 유지한다.** 남은 수량을 불변식 A 로 3건에 나눈 뒤, 3건의 감시가 · 주문가를 하나씩 차례로 수정한다. 한 건을 수정하는 동안 다른 2건이 걸려 있고, 매도 합은 늘 남은 수량 이하다. U1 결과와 상관없이 같은 순서다.
- 추적 상향도 3건을 하나씩 차례로 수정한다(조건주문 호출 한도 5/초 안).
- 감시가 ≥ 현재가이면 「익절 뒤 대기」: 손절 다리 3건 수량만 불변식 A 로 줄이고 5분마다 다시 계산.
- 추적 상향: 위로만 · 최소 폭 $0.005 또는 감시가의 0.5% 중 큰 값 · 고점은 정규장 체결가로만.

### 7-4. 시간 손절 (남은 문제 3 · Fable 막음 1 고침)
- 발표 시각 + 5거래일 안 TP1 미체결 → 다음 정규장 시작 30분 뒤부터 시작. 정규장만. 시장가 없음.
- **방법: 따로 지정가 매도를 내지 않고, 이미 걸린 손절 다리 3건의 감시가를 끌어올린다.** 그래서 손절 다리가 0건이 되는 순간이 없고, 실행기가 멈춰도 토스 서버에 보호가 남는다.
  - 1단계: 3건 감시가 = 그때 현재가 × 0.99(올림) · 주문가 = 그때 현재가 × 0.98(내림).
  - 15분 뒤 남은 다리가 있으면 2단계: 감시가 = 그때 현재가 × 0.99 · 주문가 = 그때 현재가 × 0.97. 다시 15분 뒤 3단계: 주문가 = 그때 현재가 × 0.95. 이후 15분마다 3단계를 되풀이. 기준가는 늘 「그때 현재가」다.
  - 감시가는 위로만 바꾼다(현재가가 더 내려가 감시가가 현재가 위가 되면 그대로 둔다 → 곧 발동).
- 발동되어 접수된 매도가 체결되지 않고 현재가가 그 주문가 아래로 내려가면, 10초 안에 그 주문을 취소하고 그때 현재가 × 0.95 로 다시 낸다(`accepted_sell` 은 그대로). 다시 내기가 2번 실패하면 ⑨ 긴급.
- 손절 없는 최대 시간: 0 (다리 수정 중에도 다른 2건이 걸려 있음). 다만 발동 뒤 지정가가 체결되지 않는 시간은 남는다. 이것은 일반 손절 발동과 같은 성질이고, 위 10초 다시 내기로 줄인다.
- 정규장이 끝나면 남은 다리는 7-1 대로 비상 손절 값으로 수정한다. 다음 정규장에 1단계부터 다시.
- 대표가 화면에서 「시간 손절 중지」 → 다리를 시간대 값으로 되돌린다.

### 7-5. TP1 감시 모드 (U1 거절 · U5 감소일 때)
v4 5-4절 그대로. 지정가 매도 전에 다리 축소(5절 7항). 접수된 TP1 지정가가 체결되지 않고 현재가가 TP1 × 0.99 아래로 내려가면 10초 안에 그 주문을 취소하고 다리 수량을 되돌린다(손절 없는 수량이 남는 시간을 10초로 줄임).

### 7-6. sanity (다리별)
매수 · 사다리 · 비상 손절: 감시가가 직전가 ±40% 안 / TP1: 매수가 초과 · 매수가 × 4 이하 / 추적: 감시가 < 현재가(아니면 7-3 대기) / 위반이면 등록 거부 + 알림.

## 8. 상태 기계 · 보유 인수

```
DRAFT → (대표 승인 · 쿠키 + 확인 코드 · 모의는 쿠키만) APPROVED → ENTRY_ARMED → HOLDING → (TP1 체결) TP1_WAIT 또는 TRAILING → CLOSED
ENTRY_ARMED → (마감 처리) ENTRY_RETRY → HOLDING / CANCELLED
ADOPT_PENDING → HOLDING / TRAILING
어느 상태든 → HALTED (재개 = 쿠키 + 확인 코드(모의는 쿠키만) · 다시 맞추기 뒤 불변식 통과)
```

### 8-1. 보유 인수 대기 (결정 9 · 남은 문제 10)
- 화면 「보유 인수」 승인(쿠키 + 확인 코드 · 4-2-1) → `ADOPT_PENDING`.
- 실행기가 10초마다 그 종목의 계획 밖 조건주문(앱에서 건 것)을 본다. 0건이 되는 즉시 다리 등록.
- 화면: 「앱 조건주문을 지우시면 10초 안에 실행기 손절이 걸립니다 · 그 사이 최대 10초 손절이 없습니다」를 늘 보인다. 지운 뒤 남은 초를 표시.
- 10분이 넘어도 대기를 유지하고 ⑨ 알림 1번(「앱 조건주문 n건 남음 · 인수 대기 중」). 대표가 화면에서 「인수 취소」 가능.

- 계획 밖 일반 주문(조건주문 아님) 매도가 남아 있어도 같은 대기.

### 9-1. 토큰 잠금 (남은 문제 4 · 모든 토스 호출에 걸림)
- `toss_client.py` `access_token()` · `_refresh_token()`: `backend/data/toss_token.lock` flock 을 잡고 저장 파일을 다시 읽는다. 다른 프로세스가 이미 새 토큰을 받았으면 그것을 쓴다. 정말 만료 5분 안일 때만 발급.
- 「토큰 끊김(token-revoked)」 응답: 저장 파일을 먼저 다시 읽고, 같은 토큰일 때만 잠금 안에서 새로 발급.
- 발급 가드(11/16 서버 확인으로 고침): 운영 서버 `.env` 에 `APP_ENV=production` 이 **없다**(서버 grep 0 · SOPS 키 목록에도 없음 · 코드에서는 쿠키 Secure 판단 `api/auth.py:67` 과 Sentry 표지에만 쓰임). 그래서 `APP_ENV` 를 가드로 쓰지 않는다. 새 키 `TOSS_TOKEN_ISSUE=1` 이 있을 때만 새 토큰을 발급한다. 이 키는 SOPS 에만 넣고 로컬 `.env` 에는 넣지 않는다. 까닭: 토스는 클라이언트당 토큰 1개라 로컬이 발급하면 운영 토큰이 끊긴다(10/28 로컬 발급 18회 사례).
- 키가 없으면 새 발급만 막고(예외 · ⑨ 알림 하루 1번), 이미 저장된 유효 토큰은 그대로 쓴다. 그래서 키를 빠뜨린 채 배포해도 최대 토큰 남은 시간 동안은 기존 작업이 돈다. `APP_ENV` 를 SOPS 에 넣는 길은 쿠키 Secure 자동 켜짐 같은 곁효과가 있어 쓰지 않는다.
- 배포 순서: 사용자가 SOPS 에 `TOSS_TOKEN_ISSUE=1` 을 넣는 커밋을 **코드보다 먼저** 병합한다(13절 2). 배포 뒤 확인: 서버 `grep -c '^TOSS_TOKEN_ISSUE=1' backend/.env` = 1.
- 잠금 대기 시한 10초 · 넘으면 그 호출만 오류(다른 호출이 무한히 기다리지 않음) · 저장 파일은 임시 파일에 쓰고 이름 바꾸기(원자적) · 권한 600 유지 (Fable 답 3).
- 실행기는 이벤트 루프 안이므로 동기 토스 호출은 `asyncio.to_thread` 로 돌린다.
- 영향: api · cron 의 기존 토스 호출 전부. 기존 시험 + 실제 두 프로세스 동시 발급 시험 + 발급 가드(`TOSS_TOKEN_ISSUE`)가 기존 시험을 깨지 않는지(시험은 가짜 클라이언트) 로 막는다. 가드는 `TOSS_CLIENT_ID` 와 같은 `config.get` 길로 읽는다(Fable 2차 권고 8).
