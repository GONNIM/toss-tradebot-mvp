## 1. 지킬 것

1. 실거래 스위치는 관리자 화면에서만 켠다. 켜기는 쿠키 로그인 + Origin 검사 + 텔레그램 확인 코드. 코드 · 스크립트 · 마이그레이션 · 시험은 스위치 파일에 켜짐을 쓰지 않는다(시험이 막는다).
2. 실거래 스위치는 기존 `SNIPER_LIVE_ENABLED` · `order_target` · 스나이퍼 `enabled` 와 독립이다. 계획 실행기를 켜도 스나이퍼는 켜지지 않는다.
3. 꺼져 있으면 실전 계획은 APPROVED 에서 멈추고 「실거래 꺼짐 · 새 주문 안 냄」을 보인다. 실전 계획을 모의로 대신 돌리지 않는다.
4. Kill Switch 는 기존 뜻 그대로: 새 진입 멈춤 → 계획 매수 금지 · 대기 매수 취소 · 매도 다리 유지 / 매도도 멈춤 → 계획의 모든 조건주문 취소 · HALTED.
5. 공개 저장소: 시험은 가상 종목(`TEST1`…)과 가상 가격. `.gitignore` 는 바꾸지 않는다.
6. 토스 토큰은 설정 키 `TOSS_TOKEN_ISSUE=1` 이 있는 곳(운영 서버 · SOPS 에만 둠)에서만 새로 발급한다(9-1). 실행기와 웹소켓도 같은 키가 있을 때만 시작한다. 키가 없으면 시작하지 않고 로그 1줄만 남긴다. `APP_ENV` 는 운영 서버에 없으므로(11/16 서버 확인) 판단에 쓰지 않는다. 로컬 서버 기동은 막지 않는다(`BIOTECH_API_ONLY=1 TELEGRAM_BOT_TOKEN=` 규칙 유지). 로컬 시험은 가짜 토스 클라이언트만.
7. 비밀값은 로그 · 알림 · 오류에 남기지 않는다. 계좌는 끝 4자리만. 확인 코드는 저장할 때 해시만 둔다.
8. 정해진 시각 작업은 `misfire_grace_time` · 같은 프로세스 5분 간격 · 건너뜀 알림을 갖춘다(교훈 #3 · `tests/test_job_watch.py`). 배포 금지 시간대를 지킨다.
9. 모의(paper)는 시험 전용이다. 모의 계획은 토스 주문 · 조건주문 API 를 부르지 않는다(시험이 막는다). 시세만 읽고 체결은 가상. 가상 보유 · 주문은 별도 표. 실제 계좌 보유 · 조건주문을 상태 판단에 쓰지 않는다. 모의 계획 알림은 「⑨ 실주문」이 아니라 「시스템」 범주로 보내고 「모의 시험」 표시를 붙인다(v4 1-8). 가상 체결: 감시는 모든 시간대 · 지정가는 가격이 주문가에 닿아야 체결 · 갭으로 주문가를 건너뛰면 미체결 · 감시 방향은 6-1 규칙을 똑같이 흉내 낸다(모의가 실제와 다르게 통과하지 않게 · Aside 권고 8).

- 웹소켓: 계정당 2개 한도 중 1개만 쓴다. 기존 코드에 웹소켓 사용 없음(grep 0).

| 실전 · 실제 주문 시험 계획 승인 · 보유 인수 · 그 계획의 HALTED 재개 | **쿠키만** + 텔레그램 확인 코드(4-2-1) | 있음 |
| 모의 계획 승인 · 모의 계획 HALTED 재개 | **쿠키만** | 있음 |
| 계획 정지 | 쿠키 · 헤더 모두 | 쿠키일 때 있음 |
| 스위치 끄기 · 모의 스위치 켜기 | **쿠키만** | 있음 |
| 실거래 스위치 켜기 | **쿠키만** + 텔레그램 확인 코드 | 있음 |

- 쿠키 전용 의존성은 새 인증이 아니다. 기존 관리자 확인(`api/auth.py` `_pick_token` 의 출처 구분)을 그대로 쓰고 출처가 `cookie` 일 때만 통과시킨다. 헤더면 403.
- Origin 검사: `Origin`(없으면 `Referer`)이 운영 주소와 같아야 한다. 없거나 다르면 403. 로컬은 허용 목록에 로컬 주소.
- 로그아웃 상태는 모든 계획 API 가 401. 운영 curl 로 확인하는 것이 완료 기준이다.
- 모든 성공 · 실패는 기존 접속 기록(`sniper_api_access`)에 남긴다.
- 「계획 정지」(헤더 허용)의 뜻 (Fable 권고 2): 그 계획의 새 등록 · 매수를 멈추고 대기 매수를 취소한다. **매도 다리는 지우지 않는다.** 다리를 지우는 것은 Kill Switch 「매도도 멈춤」뿐이다.
- 막음 4 (Fable) → 사용자 결정 ㉤ ① (11/16): 쿠키 값 = 관리자 토큰이라 「쿠키만 + Origin」은 토큰을 가진 쪽이 헤더를 꾸미면 통과하고, 대표 브라우저를 쓰는 Aside 도 통과한다. 그래서 실전 · 실제 주문 시험 계획 승인 · 보유 인수 · 그 계획의 HALTED 재개에 텔레그램 확인 코드를 더한다(4-2-1). 코드는 대표 휴대폰에만 오므로 토큰을 가진 쪽과 Aside 모두 혼자서는 통과하지 못한다. 모의 계획은 결정 3 대로 코드 없이 Aside 도 승인한다. 쿠키 자체를 고치는 일은 1116-02 로 그대로 둔다.
- 계획 승인 주체 칸: 실전 · 실제 주문 시험 계획 = 대표(쿠키 로그인). 모의 계획 = 대표 또는 「Aside(대표 지시)」. 실전 · 시험 계획 승인 화면에서는 Aside 표시를 고를 수 없다.

### 4-2. 실거래 켜기 확인 코드
1. 화면 「켜기」 → `POST /api/v1/plans/switches/live/challenge` → 서버가 6자리 숫자(`secrets`)를 만들고 해시 · 만든 시각 · 5분 만료 · 시도 0 을 저장, 텔레그램 「⑨ 실주문」 범주로 즉시 보냄(하루 요약 모드여도 즉시 · 코드는 알림 기록 화면에 남기지 않음).
2. 화면에 코드 입력 → `POST /api/v1/plans/switches/live {on: true, challenge_id, code, reason}` → 맞으면 켬 · 코드 즉시 무효.
3. 막는 것: 5분 지나면 무효 · 한 코드 5번 틀리면 무효 · 15분에 코드 요청 3번까지 · 새 코드를 만들면 옛 코드 무효 · 하루(KST) 실패 누적 10번이면 다음 날까지 켜기 잠금 · 실패마다 ⑨ 알림 (Fable 권고 1).
3-1. 저장은 서버 비밀값(SOPS 새 키)으로 만든 HMAC-SHA256 만 두고, 비교는 `hmac.compare_digest`(상수 시간).
4. 텔레그램 토큰이 없으면(로컬) 코드를 보낼 수 없어 켤 수 없다.

### 4-2-1. 같은 확인 코드를 승인 · 인수 · 재개에도 (결정 12 · ㉤ ①)
- 대상: 실전 · 실제 주문 시험 계획 승인, 보유 인수 승인, 그 계획의 HALTED 재개. 모의 계획 · 계획 정지 · 인수 취소 · 스위치 끄기는 코드 없음(위험을 줄이는 동작이거나 결정 3).

- 실행: 승인 · 인수 · 재개 API 가 `challenge_id` · `code` 를 함께 받는다. 코드는 **그 동작 종류 · 그 계획 번호 · 그 계획 내용 판에만** 맞는다. 다른 동작 · 다른 계획 · 실거래 켜기에 쓰면 거부한다.
- 계획 내용 판 (Fable 2차 막음 B): 계획마다 `revision`(값이 바뀔 때마다 1 늘어남)과 승인 대상 값(가격 · 수량 · 날짜 · 인수 값)의 내용 해시를 둔다. 코드를 만들 때 그 둘을 함께 저장하고, 코드를 넣을 때 다시 비교한다. 코드를 만든 뒤 값이 하나라도 바뀌면 코드는 무효이고 승인을 거부한다(「값이 바뀌었습니다 · 다시 확인해 주십시오」). 승인 대화상자는 코드를 요청하는 순간의 값을 그대로 보여 준다. 텔레그램 알림에도 판 번호를 넣는다(종목 · 금액은 넣지 않음).
- 알림 기록 (권고 6): 4-2 와 같이 세 동작의 코드도 알림 기록 · 로그에 남기지 않는다(발송기 기록에는 「확인 코드 발송」만).
- 막는 것은 4-2 3 · 3-1 과 같다. 실패로 세는 것은 틀린 코드 입력뿐이다(만료 · 무효 코드 입력은 거부만 하고 세지 않음). 「새 코드면 옛 코드 무효」는 같은 동작 · 같은 계획 안에서만이다. 잠금을 일찍 푸는 길은 두지 않는다. 15분 3번은 동작 종류별로 센다(이 값과 합산 잠금은 구현자가 정한 값 · 사용자 보고에 알림). 하루 실패 10번 잠금은 실거래 켜기와 세 동작을 합쳐 센다. 잠기면 세 동작과 실거래 켜기가 모두 다음 날까지 막힌다. 계획 정지 · 스위치 끄기 · Kill Switch 는 잠겨도 된다.
- 운영 규칙 (권고 7): Aside 가 쓰는 브라우저에는 텔레그램 웹을 로그인해 두지 않는다(12-2 체크리스트 첫 줄). Kill Switch 「매도도 멈춤」은 기존 뜻 그대로 헤더 토큰으로도 되고 계획 다리를 모두 지운다. 이때 ⑨ 긴급 알림을 보내고, 이 경로의 인증 강화는 1116-02 에서 다룬다.
- 텔레그램이 늦거나 끊기면 승인 · 인수 · 재개를 할 수 없다. 이때도 HALTED 의 보호 다리 다시 걸기(5절 10항)는 계속되므로 손절은 남는다.

## 5. 수량과 매도 예약 장부 (결정 5)

1. 계획 보유 `plan_qty` = 이 계획 매수 체결 합 − 이 계획 매도 체결 합(이 계획의 주문 번호 · 고유 키로만 셈). 인수 계획은 인수 수량에서 시작.
   - **계좌 보유 변화는 체결의 근거가 아니다** (11/18 결정 22). 체결 줄(`plan_fill`)은 토스 주문 상태 또는 사람의 확정으로만 만든다. 계좌 보유는 상한 검사(매도 합 ≤ 계좌 보유)와 경보에만 쓴다.
2. 다리 기준 수량 `base` = min(`plan_qty`, 계좌 보유). 계좌 보유가 더 적으면 알림 + 다리 축소.
3. 계획 밖 보유는 「계획 밖 보유 n주(실행기가 팔지 않음)」로 보이고 건드리지 않는다.
4. **접수된 매도 수량** `accepted_sell` = 토스에 실제 접수된 매도 주문의 남은 수량 합: 발동된 조건주문 · TP1 감시 모드 지정가 · 시간 손절 지정가. 발동 전 TP1 조건주문은 넣지 않는다. 「시간 손절 지정가」는 7-4 의 발동된 다리를 취소하고 다시 낸 지정가와, 7-4 「정리」 · 6-1 「이미 넘은 다리」로 낸 지정가를 뜻한다. 취소하고 다시 내는 동안에도 그 수량은 장부에 예약으로 남겨, 모자람 규칙이 다리를 한 번 더 걸지 않게 한다(Fable 2차 권고 2).
5. **불변식 A:** 대기 중(WATCHING) 손절 다리 수량 합 = `base` − `accepted_sell`.
6. **불변식 B:** TP1 조건주문(등록 모드) 수량 ≤ `base` − `accepted_sell` 의 ½ 내림. 이 합이 보유를 넘는 등록이 거절되면(U1) TP1 감시 모드.
6-1. **불변식 C (Fable 막음 3):** 계좌 보유 > `plan_qty`(계획 밖 보유가 있음)이면 TP1 등록 모드를 쓰지 않고 TP1 감시 모드로 강제한다. 계획의 매도 조건주문 합(TP1 포함)이 계획 밖 보유를 침범하는 순간이 없게 한다.
6-2. 같은 종목에 열린 계획은 1개만(새 계획 · 인수 모두 · Fable 권고 4).
7. 계획 매도 주문(TP1 감시 · 시간 손절)을 내기 **전에** 손절 다리를 그만큼 줄인다. 그 매도를 취소하면 원래대로.
8. 매수 주문은 계획당 동시에 1개.
9. 사다리 수량 = `base` − `accepted_sell` 을 3 으로 나눠 내림, 나머지는 마지막 단계.
10. 체결 · 전이 · 다시 맞추기 직후 불변식 검사 (Fable 막음 2). **결과를 모르는 주문(번호 없는 응답 · 시간 초과)은 이 검사의 입력이 아니라 주문 장부 대조(7-2)가 먼저 판정한다:**
   - 모름인 동안 그 수량은 묶는다. 새로 걸다 모르는 손절은 보호 수량에 세지 않고 그 수량만 다시 걸지 않는다(나머지 보호는 계속 건다). 수정하다 모르는 줄은 「옛 줄 살아 있음 + 새 줄 모름」 으로 함께 두고, 넘침 검사에는 둘 다 세고 보호 수량에는 확인된 것만 센다.
   - 매도 예약이 모름이면 예약을 풀지 않고 그 수량만 묶는다. 묶인 수량은 손절이 없으므로 ⑨ 긴급 알림을 10분마다 되풀이한다.
   - **모자람**(손절 합 < `base` − `accepted_sell`): 닫힌 조건주문(발동 · 체결 이력)과 체결을 먼저 다시 읽어 `base`·`accepted_sell` 을 고친 뒤, 그래도 모자라면 모자란 수량만큼 보호 다리를 다시 건다. HALTED 상태에서도 이 「보호 다리 다시 걸기」는 허용한다. ⑨ 알림.
   - **넘침**(손절 합 > 기준) 또는 짝이 여럿: 새 등록을 멈추고 HALTED + ⑨ 긴급. 넘친 다리 축소(수량 줄이기 · 취소)는 HALTED 에서도 한다.
   - 정상 넘침 (Fable 2차 권고 3): TP1 · 손절 다리가 발동해 `accepted_sell` 이 늘어난 직후 다른 다리를 줄이는 것은 정상 처리다. 이때는 넘침으로 보지 않고 바로 줄인다. 줄이기가 3번 실패할 때만 넘침으로 본다.
   - 다시 거는 보호 다리의 값 · HALTED 중 시간대 교대 (권고 4): 다시 거는 다리는 그때 시간대 값(7-1)으로 건다. HALTED 에서도 시간대 교대 수정은 한다(보호를 지키는 동작).
   - HALTED 에서 허용: 보호 다리 다시 걸기 · 넘친 다리 줄이기 · 시간대 교대 수정 · 6-1 즉시 매도와 그 거절 뒤 다시 걸기 · 다시 맞추기. 금지: 매수 · 다리 위로 올리기 · TP1 · 시간 손절.

### 6-1. 감시 방향 규칙 (3판 · Aside 막음 1 · 권고 2 · 3)
- 사실: 조건주문 본문에는 방향 칸이 없다(`triggerPrice` 「현재가가 이 값에 닿으면 주문을 생성」 · openapi.json 1.2.28 · 11/16 확인). OCO 예시는 「first 감시가 > 현재가 > second 감시가」다. 토스 앱 유의사항(Aside 확인)은 「감시가 < 현재가 → 이하 · 감시가 > 현재가 → 이상 · 같으면 매도 이상 · 매수 이하」이고, FAQ 는 Open API 조건주문을 앱과 같은 방식으로 감시한다고 적는다. 해외 조건주문이 모든 시간대에 발동한다는 것은 명세(`POST /conditional-orders` 설명 「장 구분과 상관없이, 거래 가능한 모든 시간대에 발동」)로 확인된다. 수정은 취소 뒤 새 번호 · WATCHING · PAUSED 만 · 판정 중이면 `modify-restricted` 로 거절될 수 있다(명세). 수정은 취소 뒤 새로 만들기라 수정마다 방향이 다시 정해진다. **그래서 등록 · 수정 순간 현재가가 감시가의 어느 쪽에 있는지가 방향을 정한다고 본다(추정 · U8 로 확정).**
- 규칙: 모든 조건주문을 등록 · 수정하기 **직전에** 현재가를 읽는다(웹소켓 최근 체결 · 10초보다 오래됐으면 `GET /prices`). 그리고 아래로 나눈다. 1틱 = 6절 가격 단위.
  - 비교 기준(Fable 3판 막음 1): 「아래에 있음」 = 감시가 ≤ 현재가 − 1틱 · 「위에 있음」 = 감시가 ≥ 현재가 + 1틱. 끌어올리기(7-4) · 추적 상향(7-3)이 만드는 매도 감시가는 늘 min(계산값, 현재가 − 2틱)으로 둬서 1틱 여유가 남게 한다. 7-3 추적 전환 조건과 7-6 추적 sanity 도 같은 기준을 쓴다.
  - **매도 손절 · 추적 · 비상 · 시간 손절 다리:** 감시가가 현재가 아래에 있으면(≤ 현재가 − 1틱) 조건주문으로 건다. 아니면(이미 넘은 다리) 조건주문으로 걸지 않는다. 그 수량은 즉시 지정가 매도로 내고 매도 예약 장부에 올린다. 주문가는 정규장이면 현재가 × 0.98, 정규장 밖에서 지정가가 되는 세션이면 × 0.97(내림)이다. 그 세션에 지정가를 낼 수 없으면 기존 다리를 고치지 않고 그대로 두고 ⑨ 긴급 알림을 보낸다. 매도를 내기 전에 그 다리를 그 수량만큼 먼저 줄이고(5절 7항 · 매도 합이 보유를 넘지 않게) 바로 지정가 매도를 낸다. 그래서 그 다리 수량만 약 1초 보호가 비고, 다른 다리는 걸려 있다. 매도가 거절되면 즉시 그 다리를 6-1 로 다시 건다. 미체결 처리는 7-4 「10초 다시 내기」와 같다.
  - **TP1 (등록 모드):** 감시가 ≥ 현재가 + 1틱 이면 조건주문. 아니면(이미 넘음) TP1 감시 모드 처리(7-5)로 즉시 지정가 매도.
  - **매수:** 감시가 ≤ 현재가 − 1틱 이면 조건주문. 아니면(이미 매수가 아래) 조건주문 대신 일반 지정가(DAY) 매수를 낸다. 진입 창 동안 매 정규장 시작 1분 뒤 같은 조건으로 다시 낸다(매수 1개 원칙 유지). 마감 처리 · 실거래 끄기 취소 대상에 이 일반 주문도 넣는다.
- 낮은 현재가 확인 (Fable 3판 권고 2): 「이미 넘음」으로 즉시 매도하기 전에 웹소켓 최근 체결과 `GET /prices` 두 값이 서로 1% 안에서 같고 둘 다 감시가 이하일 때만 처리한다. 확인하는 동안(최대 10초) 옛 다리는 그대로 둔다. 한쪽만 낮으면 이상값으로 보고 다음 체결을 기다린다.
- 대기 매수 먼저 취소 (권고 3): 계획 매도(6-1 즉시 매도 · TP1 감시 · 시간 손절)를 내기 전에 그 계획의 대기 매수(일반 지정가 · 매수 조건주문)를 먼저 취소한다. `POST /orders` 의 `opposite-pending-order-exists` 를 피하기 위해서다. 조건주문 발동으로 생기는 매도도 같은 오류에 막히는지는 U9 로 확인한다.
- 매도 거절 · 되풀이 (막음 2): 즉시 매도가 거절되면 그 수량의 다리를 「6-1 을 통과하는 값」으로 다시 건다. 옛 다리 값이 통과하면 옛 값, 아니면 그때 현재가 × 0.85(비상 손절 폭 · 감시가 올림 · 주문가 × 0.97 내림)다. 같은 다리에서 거절 · 다시 걸기가 3번 되풀이되면 더 시도하지 않고, 통과하는 다리만 남긴 채 ⑨ 긴급 + HALTED.
- HALTED 에서도 6-1 즉시 매도는 허용한다(위험을 줄이는 동작 · 5절 10항 허용 목록에 넣음). 단 시간 손절 단계 진행(끌어올리기 · 정리)은 HALTED 에서 멈춘다.
- 토스가 「조건 이미 충족」 류 오류로 등록을 거절하면 같은 「이미 넘은」 처리로 간다(옛 문서의 `condition-already-met` · 1.2.28 명세에는 없음).
- 현재가를 읽은 뒤 등록까지 1초 안에 가격이 지나가는 경우가 남는다. 그래서 등록 응답 뒤 그 다리를 다시 읽어 감시가와 그때 현재가를 다시 비교한다. 방향이 뒤집혔다고 판단되면 그 다리를 취소하고 위 「이미 넘은」 처리를 한다.
- 구현 (권고 1): 6-1 은 브로커의 조건주문 등록 · 수정 · 일반 주문 함수 **한 곳**에서만 거친다. 그 밖에서 토스 조건주문 · 주문 API 를 직접 부르는 코드가 0 임을 시험으로 막는다. 토스 수정은 전체 다시 만들기라 수량만 바꿔도 방향이 다시 정해지므로 수량 축소 수정도 거친다.
- 걸리는 경로 예시(이 목록이 전부가 아니다): 첫 등록 · 시간대 교대(7-1) · 추적 상향(7-3) · 시간 손절(7-4) · 보호 다리 다시 걸기(5절 10항) · 인수 첫 등록(8-1) · HALTED 중 시간대 교대 · 수량 축소 수정(5절 7·10항 · 7-3 익절 뒤 대기) · 추적 전환 첫 수정 · 7-5 TP1 취소 뒤 수량 되돌리기 · 7-2 수정 다시 시도 · 4-3 취소 중 일부 체결 뒤 다리 · ENTRY_RETRY 매수 다시 등록 · 만료일 연장 수정.
- 만료일 (권고 5 · v4 U3 · 5-1): `expireDate` 는 필수이고 최대 1년이다. 매수 조건주문 = 마감 거래일 다음 거래일(v4). 매도 다리 = 등록일 + 90일. 남은 기간이 10일 아래면 다시 맞추기가 같은 값으로 수정해 연장한다(6-1 거침). 다시 맞추기에서 EXPIRED 가 된 계획 다리는 「모자람」으로 다룬다.

## 7. 계획 값 · 다리

v4 4~5절 그대로 + 아래 고침.

### 7-1. 시간대 다리
- 장 시간은 `GET /api/v1/market-calendar/US` 를 매일 읽는다(기존 `execution/market_calendar.py`).
- 아래쪽 다리는 늘 SINGLE SELL 3건. 시간대가 바뀌면 같은 3건을 **수정**(토스는 취소 뒤 새 번호 · WATCHING·PAUSED 만).
- 정규장: 사다리 · 주문가 = 감시가 × 0.98 / 정규장 밖(데이 · 프리 · 애프터): 3건 모두 비상 손절 −15% · 주문가 × 0.97.
- 전환 시각: 정규장 시작 1분 뒤 · 종료 1분 뒤. 전환 수정은 다리마다 6-1 을 먼저 거친다(갭 하락으로 사다리 값이 이미 현재가 위면 그 다리는 즉시 지정가 매도).
- 수정 실패: 3초 뒤 다시 조회 · 다시, 3번 실패면 HALTED + 알림. 수정 실패 뒤 옛 주문이 남는지는 확인되지 않았다(U7 · 소액 시험). 다시 조회했을 때 옛 주문도 새 주문도 없으면 5절 10항 「모자람」으로 즉시 보호 다리를 다시 건다.

### 7-2. 주문 장부와 결과 모르는 주문 대조 (11/18 결정 21 · 22 로 다시 씀 · 옛 「수정 중 기록」 대체)
- 토스로 **보낼 때마다 장부 한 줄**(`plan_order_book`)을 먼저 남기고 commit 한 뒤 호출한다. 칸: clientOrderId · 종류(조건/일반) · 역할 · 수량 · 가격 · 토스 번호 · 부모 줄 · 바꾸려던 옛 줄 · 상태 · 보낸 시각. 보낼 때마다 새 clientOrderId 를 쓴다(같은 키로 다시 내지 않는다).
- 상태: 보냄-모름 · 열림 · 닫힘 · 안 만들어짐 · 사람 확인.
- **대조 함수 하나**(`orderbook.reconcile`)가 다리 · 매도 예약 · 수정 · 단건 조회가 빈 값인 경우의 판정을 대신한다. 규칙:
  1. 낸 뒤 설정 시간(`PLAN_ORDER_SETTLE_SEC` · 기본 90초) 안에는 「없음」으로 단정하지 않는다.
  2. 목록에서 clientOrderId 로 찾을 수 있는지를 설정(`PLAN_ORDER_LIST_SEARCHABLE`)으로 받고 **기본값은 「못 찾음」** 이다. 못 찾음이면 모르는 주문은 모두 「그 수량 묶음 + 사람 확인」 으로 간다. 소액 시험(U6)에서 확인되면 설정만 바꾼다.
  3. 목록 쪽 나눔 · 보관 기간을 아는지를 설정(`PLAN_ORDER_LIST_PAGING_KNOWN` · 기본 「모름」)으로 받는다. 모르는 동안에는 목록에 없다는 것을 「안 만들어짐」 근거로 쓰지 않는다.
  4. 같은 clientOrderId 가 둘이면 자동 연결하지 않는다. **값 일치(수량 · 감시가 · 주문가) 자동 연결은 없다** — 후보를 사람에게 보여 주기만 하고, 후보가 여럿이어도 기록은 사람이 풀 수 있다.
  5. 수정은 토스에서 한 번의 호출이다. 옛 주문이 남는지는 U7 이라 장부에 「옛 줄 열림 + 새 줄 보냄-모름」 이 함께 있을 수 있다.
  6. 발동된 조건주문의 자식 주문은 부모 줄 아래 적는다(부모 조건주문 – 자식 주문 관계). 상태를 모르면(UNKNOWN) 닫힘으로 보지 않고 예약을 유지하며 알린다.
  7. 단건 조회가 빈 값이면 바로 CANCELED 로 두지 않고 열린 · 닫힌 목록에서 번호를 찾고, 못 찾으면 사람 확인으로 보낸다.
- 사람 확인: 화면의 「결과 모르는 주문」 에서 「체결 n주 / 안 만들어짐 / 열려 있음(번호)」 을 확정한다(쿠키 전용 + 실전 · 시험 계획이면 정지 풀기와 같은 텔레그램 코드). 체결을 확정하면 사람이 정한 수량만 체결 줄에 적는다. 확인이 끝나기 전에는 정지를 풀 수 없다.
- 계좌 보유는 이 판정에 쓰지 않는다. 매수가 모름인데 계좌 보유가 늘면 ⑨ 긴급 알림만 보낸다(자동으로 체결을 적지 않음).

### 7-3. 익절 뒤 (남은 문제 1 · 2)
- TP1 체결 → 추적 감시가 = max(평단, 정규장 고점 × 0.85) 를 계산.
- 감시가 ≤ 현재가 − 1틱(6-1 「아래에 있음」)이면 추적 전환 (Fable 막음 3 고침): **추적 손절도 3건을 유지한다.** 남은 수량을 불변식 A 로 3건에 나눈 뒤, 3건의 감시가 · 주문가를 하나씩 차례로 수정한다. 한 건을 수정하는 동안 다른 2건이 걸려 있고, 매도 합은 늘 남은 수량 이하다. U1 결과와 상관없이 같은 순서다.
- 추적 상향도 3건을 하나씩 차례로 수정한다(조건주문 호출 한도 5/초 안).
- 그렇지 않으면 「익절 뒤 대기」: 손절 다리 3건 수량만 불변식 A 로 줄이고 5분마다 다시 계산.
- 추적 상향: 위로만 · 최소 폭 $0.005 또는 감시가의 0.5% 중 큰 값 · 고점은 정규장 체결가로만. 3건 수정마다 6-1 을 거친다.
- 고점 값 (Aside 권고 5): 고점은 정규장 1분봉 종가의 최고값으로 잡는다. 직전 고점보다 한 번에 10% 넘게 높은 값은 다음 1분봉 종가가 그 값의 3% 안에서 확인해 줄 때까지 보류한다. 장외 · 특수 체결 값은 쓰지 않는다(토스 FAQ: 미국 체결에 장외 · 특수 가격이 섞이고 거르지 않음). 시간 손절 · 6-1 의 「현재가」도 같은 이상값 보류를 쓴다.

### 7-4. 시간 손절 (Fable 막음 1 · 대표 결정 ㉥ ①)
- 발표 시각 + 5거래일 안 TP1 미체결 → 다음 정규장 시작 30분 뒤부터 시작. 정규장만. 시장가 없음. 뜻은 v4 대로 「정리」다(㉥ ①).
- **끌어올리기 (그 정규장 1세션만):** 이미 걸린 손절 다리 3건의 감시가를 끌어올린다. 손절 다리가 0건이 되는 순간이 없다.
  - 1단계: 3건 감시가 = min(그때 현재가 × 0.99 올림, 현재가 − 2틱) · 주문가 = 그때 현재가 × 0.98(내림). ($1.00~$1.99 에서도 1단계가 곧바로 즉시 매도가 되지 않게 함 · Fable 3판 막음 1) 15분마다 같은 계산으로 위로만 다시 수정한다. 수정마다 6-1 을 거친다(급락으로 이미 넘은 다리는 즉시 지정가 매도).
- **정리:** 그 정규장 종료 30분 전까지 남은 다리는 1건씩 6-1 「이미 넘은 다리」 처리로 지정가 매도한다(주문가 = 그때 현재가 × 0.98 내림 · 다리를 먼저 줄인 뒤 바로 매도). 1건이 접수된 뒤 다음 건으로 간다.
- 접수된 매도가 체결되지 않고 현재가가 그 주문가 아래로 내려가면, 10초 안에 그 주문을 취소하고 그때 현재가 × 0.95 로 다시 낸다(`accepted_sell` 은 그대로 · 5절 4항). 취소 뒤 남은 수량을 다시 읽고 그 수량만 다시 낸다. 다시 내기가 2번 실패하면 예약을 풀고 그 수량의 보호 다리를 6-1 로 다시 건 뒤 ⑨ 긴급(주문도 다리도 없는 수량을 남기지 않음 · 권고 4).
- 정규장이 끝날 때까지 체결되지 않은 매도는 종료 1분 전에 취소하고, 그 수량은 7-1 비상 손절 값의 다리로 되돌린다(6-1 거침). 다음 정규장 시작 30분 뒤 「정리」부터 다시 한다(끌어올리기는 다시 하지 않음).
- 손절 없는 최대 시간(끌어올리기 단계): 전체 0 · 다리 1건 수량만 약 1초(줄인 뒤 매도 접수까지). 정리 단계에서는 다리가 지정가 매도로 바뀌므로 보호는 접수된 지정가와 10초 다시 내기가 맡는다. 다리 수정 중에도 다른 다리가 걸려 있다. 다만 접수된 지정가가 체결되지 않는 시간은 남는다(일반 손절 발동과 같은 성질 · 10초 다시 내기로 줄임).
- 대표가 화면에서 「시간 손절 중지」 → 끌어올리기 · 정리를 멈추고 남은 다리를 시간대 값으로 되돌린다(6-1 거침).

### 7-5. TP1 감시 모드 (U1 거절 · U5 감소일 때)
v4 5-4절 그대로. 지정가 매도 전에 다리 축소(5절 7항). 등록 모드의 TP1 이 등록 · 수정 순간 이미 넘어 있으면(6-1) 이 감시 모드 처리로 즉시 지정가 매도한다(Aside 권고 2). 접수된 TP1 지정가가 체결되지 않고 현재가가 TP1 × 0.99 아래로 내려가면 10초 안에 그 주문을 취소하고 다리 수량을 되돌린다(손절 없는 수량이 남는 시간을 10초로 줄임).

### 7-6. sanity (다리별)
매수 · 사다리 · 비상 손절: 감시가가 직전가 ±40% 안 / TP1: 매수가 초과 · 매수가 × 4 이하 / 추적: 감시가 ≤ 현재가 − 1틱(아니면 7-3 대기) / 위반이면 등록 거부 + 알림.
11/18 결정(㉤): 이 점검은 조건주문 등록 · 수정에만 건다. 이미 넘은 다리의 즉시 지정가 매도는 막지 않는다(폭락 때 손절이 막히지 않게). 대신 즉시 매도는 ① 방금 다시 읽은 현재가로 주문가를 정하고 ② 수량을 min(요청 수량, 계획 수량 · 계좌 보유 중 작은 값 − 이미 접수된 매도) 로 제한한다.

## 8. 상태 기계 · 보유 인수

```
DRAFT → (대표 승인 · 쿠키 + 확인 코드 · 모의는 쿠키만) APPROVED → ENTRY_ARMED → HOLDING → (TP1 체결) TP1_WAIT 또는 TRAILING → CLOSED
ENTRY_ARMED → (마감 처리) ENTRY_RETRY → HOLDING / CANCELLED
ADOPT_PENDING → HOLDING / TRAILING
어느 상태든 → HALTED (재개 = 쿠키 + 확인 코드(모의는 쿠키만) · 다시 맞추기 뒤 불변식 통과)
```

### 8-0. 보유 인수 입력 (v4 6-2 그대로 + 8-1 고침 · Aside 권고 7)
- 입력: 종목 · 인수 수량(계좌 보유 이하) · 기준 평균가(기본 = 토스 평단 · 수정 가능) · 손절 폭 · TP1 · 발표 시각.
- 「추적 단계로 인수」(앱에서 이미 TP1 을 팔았을 때): TRAILING 으로 시작. 고점 시작값은 대표 입력, 기본 = 인수 직전 정규장 1분봉 종가 최고값(7-3 고점 규칙) · 감시 하한 = 기준 평균가.
- v4 6-2 의 「앱 조건주문이 남아 있으면 승인 거부」는 결정 9(8-1 인수 대기)로 바꿨다: 승인 → 대기 → 앱 조건주문을 지우면 10초 안에 등록. 인수 첫 등록도 6-1 을 거친다.
- 인수 시작에는 실거래 스위치가 켜져 있어야 한다(4-3).

### 8-1. 보유 인수 대기 (결정 9 · 남은 문제 10)
- 화면 「보유 인수」 승인(쿠키 + 확인 코드 · 4-2-1) → `ADOPT_PENDING`.
- 실행기가 10초마다 그 종목의 계획 밖 조건주문(앱에서 건 것)을 본다. 0건이 되는 즉시 다리 등록.
- 화면: 「앱 조건주문을 지우시면 10초 안에 실행기 손절이 걸립니다 · 그 사이 최대 10초 손절이 없습니다」를 늘 보인다. 지운 뒤 남은 초를 표시.
- 10분이 넘어도 대기를 유지하고 ⑨ 알림 1번(「앱 조건주문 n건 남음 · 인수 대기 중」). 대표가 화면에서 「인수 취소」 가능.
- 실거래 스위치가 꺼져 있으면 인수를 시작하지 않는다(4-3).
- 계획 밖 일반 주문(조건주문 아님) 매도가 남아 있어도 같은 대기.

### 9-1. 토큰 잠금 (남은 문제 4 · 모든 토스 호출에 걸림)
- `toss_client.py` `access_token()` · `_refresh_token()`: `backend/data/toss_token.lock` flock 을 잡고 저장 파일을 다시 읽는다. 다른 프로세스가 이미 새 토큰을 받았으면 그것을 쓴다. 정말 만료 5분 안일 때만 발급.
- 「토큰 끊김(token-revoked)」 응답: 저장 파일을 먼저 다시 읽고, 같은 토큰일 때만 잠금 안에서 새로 발급.
- 발급 가드(11/16 서버 확인으로 고침): 운영 서버 `.env` 에 `APP_ENV=production` 이 **없다**(서버 grep 0 · SOPS 키 목록에도 없음 · 코드에서는 쿠키 Secure 판단 `api/auth.py:67` 과 Sentry 표지에만 쓰임). 그래서 `APP_ENV` 를 가드로 쓰지 않는다. 새 키 `TOSS_TOKEN_ISSUE=1` 이 있을 때만 새 토큰을 발급한다. 이 키는 SOPS 에만 넣고 로컬 `.env` 에는 넣지 않는다. 까닭: 토스는 클라이언트당 토큰 1개라 로컬이 발급하면 운영 토큰이 끊긴다(10/28 로컬 발급 18회 사례).
- 키가 없으면 새 발급만 막고(예외 · ⑨ 알림 하루 1번), 이미 저장된 유효 토큰은 그대로 쓴다. 그래서 키를 빠뜨린 채 배포해도 최대 토큰 남은 시간 동안은 기존 작업이 돈다. `APP_ENV` 를 SOPS 에 넣는 길은 쿠키 Secure 자동 켜짐 같은 곁효과가 있어 쓰지 않는다.
- 배포 순서: 사용자가 SOPS 에 `TOSS_TOKEN_ISSUE=1` 을 넣는 커밋을 **코드보다 먼저** 병합한다(13절 2). 배포 뒤 확인: 서버 `grep -c '^TOSS_TOKEN_ISSUE=1' backend/.env` = 1.
- 잠금 대기 시한 10초 · 넘으면 그 호출만 오류(다른 호출이 무한히 기다리지 않음) · 저장 파일은 임시 파일에 쓰고 이름 바꾸기(원자적) · 권한 600 유지 (Fable 답 3).
- 실행기는 이벤트 루프 안이므로 동기 토스 호출은 `asyncio.to_thread` 로 돌린다.
- 영향: api · cron 의 기존 토스 호출 전부. 기존 시험 + 실제 두 프로세스 동시 발급 시험 + 발급 가드(`TOSS_TOKEN_ISSUE`)가 기존 시험을 깨지 않는지(시험은 가짜 클라이언트) 로 막는다. 가드는 `TOSS_CLIENT_ID` 와 같은 `config.get` 길로 읽는다(Fable 2차 권고 8).
