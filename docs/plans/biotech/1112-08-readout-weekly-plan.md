## 3. 설계
1. 기간 순수 함수: 앞 기간 complete 이고 (미국 동부 어제 − 앞 until) ≥ 7일이면 새 기간 since = 앞 until − 3일 · until = 미국 동부 어제. 아니면 같은 기간 이어 받기. 첫 서버 실행은 docs 본 until(11/12) 기준 → since 11/09.
2. 막음 ①: 기간이 바뀔 때와 실행 시작 때 `complete=False` 로 쓰고, 끝까지 받았을 때만 True.
3. 막음 ②: 매 22:00 실행마다(할 일 없어도) `last_run_at` 칸을 쓴다. 멈춤 판단은 이 칸으로 한다.
4. 막음 ③: 이미 본 접수번호 = WP39 명부 + docs 본 + RUNTIME 본 사건 + 검색어 없던 본문 접수번호(파일에 저장 · 최근 두 기간 것만 보관).
5. 장부: 요청마다 다시 읽고 더해 저장(`save_ledger_merged` 방식) · 보내기 직전 합계 + 1 > 300 이면 멈춤(종료 3) · 실행 중 KST 날짜가 바뀌면 멈춤.
6. 잠금: 같은 스크립트 겹쳐 실행 금지(파일 잠금). 22:00~22:15 배포는 피하고, 겹쳐 빠진 날은 다음 날 이어 받기로 메운다.
7. 새 사건 티커는 `sec_company_tickers.json`(요청 0)으로 채운다. docs 본 6건은 그대로.
8. 알림(텔레그램 warning · 원인 코드 · 같은 원인 하루 1번 · 매수·매도 권유 문장 없음): 403/429/410/401 즉시 · 이틀 연속 403/429 면 자동 실행 멈춤(사람이 다시 켬) · 500·전송 오류 이틀 연속 · 기간 연 뒤 7일 넘게 덜 끝남(처리 N/340 · 까닭) · 07:00 파이프 `--check-stale`(요청 0 · until 9일 넘거나 last_run_at 3일 멈춤).
9. 계속 오류인 회사는 실패 목록에 적고 7일 뒤 그 기간을 닫는다(알림에 회사 수).
10. 통계는 기간별로 따로 남긴다.
11. 백업: 03:30 백업이 `var/biotech` 를 담는지 구현 때 확인 · 잃으면 다시 받는 데 드는 요청 수를 운영 문서에 적는다.
