## 1. v5 → v6 Diff (D3 교체 문안 반영)

### D3 재결함 (v5)

**Fable 5 5차 지적 (원문)**:
> "(b) 방식 자체는 옳으나 구현 순서가 자기모순. v4 §2.2 에서 /verification API 는 Step B 산출물. 그런데 v5 의 serenity_hunter_step_gate job 은 Step B whitelist 경로 (serenity_hunter.py) 커밋을 감지하면 /verification 을 curl · Step B 배포 전엔 404 이므로 첫 Step B 배포는 반드시 CI fail · 배포가 막히니 엔드포인트는 영원히 생기지 않음.
>
> 부수 결함: 검증식이 .hero.gate_open 인데 · gate_open 은 health.warn · deprecation 까지 AND. 크롤러 일시 장애로 warn=true 인 날 Step B 배포가 무관한 사유로 막힘. CI 가 물어야 할 것은 데이터 충분성 (events ≥50 · benchmark rows ≥50) 이지 운영 상태가 아님."

### v6 교체 (Fable 5 5차 문안 그대로)

**① 엔드포인트 Step 소속 이관**

| 산출물 | v5 소속 | v6 소속 |
|---|---|---|
| `backend/api/routes/serenity_hunter.py` · `/api/v1/serenity/verification` (백엔드) | **Step B** | **Step A** |
| `backend/api/routes/serenity_hunter.py` · `/api/v1/serenity/health` (백엔드) | **Step B** | **Step A** |
| `backend/api/routes/serenity_hunter.py` · `/api/v1/serenity/hunter` (백엔드) | Step C | Step C (불변) |
| `frontend/app/influencer/serenity-hunter/**` · Hero/Bucket UI | Step B | Step B (불변 · UI 만) |
| `frontend/app/influencer/serenity-hunter/**` · HunterTable/EmptyGate/MidGateWarning UI | Step C | Step C (불변) |

**Step 재정의**:

| Step | v5 목표 | v6 목표 |
|---|---|---|
| **A** | 백테스트 확장 + 검증 데이터 수집 (**API 없음**) | 백테스트 확장 + 검증 데이터 수집 + **`/verification` + `/health` API 배포** (백엔드 완결 · 프론트 없음) |
| **B** | `/verification` API + Hero/Bucket UI | **Hero/Bucket UI 만** (API 는 이미 Step A 에 있음) |
| **C** | `/hunter` API + HunterTable + 폐기 조건 + 리스크 문서 | 동일 · 불변 |

**결과**: Step B 시점에는 `/verification` API 가 이미 서버에 존재 (Step A 산출물) → CI curl 404 데드락 해소.

**② CI whitelist 재정의**

| 위치 | v5 | v6 |
|---|---|---|
| `.github/workflows/deploy.yml::serenity_hunter_step_gate` trigger | `backend/api/routes/serenity_hunter.py` · `frontend/app/influencer/serenity-hunter/**` | **`frontend/app/influencer/serenity-hunter/**` 만** (backend routes 는 Step A 배포 시 자동 배포 · gate 불요) |

**③ CI 검증식 재정의 (gate_open 사용 금지)**

| 위치 | v5 | v6 |
|---|---|---|
| serenity_hunter_step_gate job 검증식 | `curl -sf .../verification | jq -e '.hero.gate_events_have >= 50 and .hero.gate_open'` | `curl -sf .../verification | jq -e '.hero.gate_events_have >= 50 and .hero.gate_events_needed <= .hero.gate_events_have'` + 별도로 `.hero.benchmark: {iwm}` row 필드 확인 (예: `jq -e '(.hero.gate_events_have >= 50) and ((.hero.benchmark.iwm | length) > 0)'` 형태) |

**gate_open 제거 이유** (Fable 5 5차):
- gate_open 은 health.warn AND deprecation_triggered AND 데이터 충분성 · 세 조건 AND
- CI 가 물어야 할 것은 **데이터 충분성만** (Step 순서 강제 목적)
- 운영 상태 (health.warn) 나 폐기 상태 (deprecation) 는 **런타임 게이트가 담당** · CI 는 배포 순서 강제만 담당
- 크롤러 일시 장애 · 폐기 발동 등 무관한 사유로 Step B UI 배포 차단되면 안 됨

**④ §2.12 Verification 방법 Step A 완료 항목 추가**

| 위치 | v5 | v6 |
|---|---|---|
| §2.12 Step A 완료 항목 | 1~5 · SQL 카운트 · 크론 로그 · pytest · `.step_a_gate_ok` marker (v5 에서 이미 삭제) | + **6. `curl -sf https://optimus8.cafe24.com/api/v1/serenity/verification` 응답 200 확인** · `jq '.hero.gate_events_have'` ≥ 50 눈으로 확인 |
