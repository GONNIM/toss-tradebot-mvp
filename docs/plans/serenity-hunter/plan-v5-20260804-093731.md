## 1. v4 → v5 Diff 요약

### D1. 비용·슬리피지 차감 정의 일원화 (v4 최대 결함)

**Fable 5 지적 (원문)**:
> "슬리피지·비용 조정이 세 겹으로 존재: ① `entry_with_slippage_price` (수익률 계산 분모) ② `excess_return(sig, bench, cost)` = sig−bench−cost ③ 폐기식 `avg(excess_return_3d_iwm) − SLIPPAGE_PCT − COST_ROUND_TRIP_PCT ≤ 0`. ①로 계산한 return 을 ②에 넣고 ③에서 또 빼면 슬리피지 2회 · 비용 2회 차감. 이중 차감이면 폐기 과잉 발동 (기회 손실) · 반대면 미차감 구간. 어느 쪽이든 최종 판정 숫자가 틀림."

**v5 원칙 (정의 일원화)**:
> **저장은 raw · 조정은 표시/판정 계층에서 각 1회만**

**구체 변경**:

| 위치 | v4 | v5 |
|---|---|---|
| `SerenityBacktest.return_1d/3d/...` | slippage 반영된 값 (entry_with_slippage_price 기반) 저장 | **raw return · 다음 거래일 시가 (`entry_next_open_price`) 기준 무조정 수익률** 저장 |
| `entry_with_slippage_price` | 저장 컬럼 유지 | **참고용 저장 유지** (표시에만 사용 · 계산 진입점 아님) |
| `backtest.py::excess_return()` | `sig_ret − bench_ret − cost_pct` (cost 인자 존재) | `sig_ret − bench_ret` · **`cost_pct` 인자 제거** · 순수 초과수익만 반환 |
| `hero.avg_cost_adjusted_return_1d` | (v4 존재 · 계산 방식 불명) | `avg(raw_return_1d) − SLIPPAGE_PCT − COST_ROUND_TRIP_PCT` · **표시 계층 1회 차감** |
| `hero.avg_slippage_adjusted_return_1d` | 존재 | `avg(raw_return_1d) − SLIPPAGE_PCT` · **표시 계층 1회 차감 · slippage만** |
| 폐기식 (`is_deprecation_triggered()`) | `avg(excess_return_3d_iwm) − SLIPPAGE_PCT − COST_ROUND_TRIP_PCT ≤ 0` | `avg(raw_return_3d − benchmark_iwm_return_3d) − SLIPPAGE_PCT − COST_ROUND_TRIP_PCT ≤ 0` · **판정 계층 1회 차감** (excess 는 raw · slippage/cost 는 여기서만) |
| 중간 경고식 (`mid_gate_excess_warning()`) | (v4 슬리피지·비용 표기 애매) | 동일 원칙 · `avg(raw − bench_iwm) − SLIPPAGE − COST ≤ 0` |

**차감 위치 최종 (v5)**:
- ① **저장 계층**: 무조정 (raw)
- ② **표시 계층**: `hero.avg_slippage_adjusted_return_*` (slippage 1회) · `hero.avg_cost_adjusted_return_*` (slippage+cost 1회씩)
- ③ **판정 계층**: 폐기식 · 중간경고식 각 1회씩만
- excess_return() 함수는 순수 초과수익 (bench 만 차감) · cost 인자 삭제

**추가 방어 (옆문 마찰)**:
- `backend/tests/serenity/test_constants_hardening.py` (신규):
  ```python
  def test_cost_and_slippage_not_lowered():
      from backend.discovery.serenity.constants import COST_ROUND_TRIP_PCT, SLIPPAGE_PCT
      assert COST_ROUND_TRIP_PCT >= 1.0, "실측 하향 시 이 테스트도 함께 갱신 · git diff 노출 필수"
  ```

### D2. confidence 예측력 판정 3상태화

**Fable 5 지적 (원문)**:
> "15%p AND 양쪽 n≥30 은 N 이 150 도달 전 구간에서 구조적으로 min_n_ok=false (3분위 균등 분할 시 n≥30 은 valid ≥ 90 근방부터). 미달 시 컬럼 삭제 티켓 자동 생성이라 표본 부족 상태를 '예측력 없음' 오판 · 티켓 오발행. predictive_pass 를 3상태로 나눠라: insufficient_n / fail / pass · 삭제 티켓은 fail 에서만."

**구체 변경**:

| 위치 | v4 | v5 |
|---|---|---|
| `verification.py::confidence_predictive_check()` return | `{top_hit_rate, bottom_hit_rate, diff_pp, min_n_ok, predictive_pass: bool}` | `{top_hit_rate, bottom_hit_rate, diff_pp, top_n, bottom_n, min_n_ok, predictive_status: "insufficient_n" \| "fail" \| "pass"}` |
| 판정 로직 | `predictive_pass = (diff_pp >= 15) and min_n_ok` | 3상태:<br>• `min_n_ok=false` → `"insufficient_n"` (대기 · 티켓 없음)<br>• `min_n_ok=true AND diff_pp < 15` → `"fail"` (컬럼 삭제 티켓 발행)<br>• `min_n_ok=true AND diff_pp >= 15` → `"pass"` |
| `scripts/serenity_confidence_predictive_check.py` | `predictive_pass=false` 시 티켓 발행 | `predictive_status=="fail"` 시에만 티켓 발행 · `insufficient_n` 시 `logger.info` 만 |
| API `/verification` 응답 필드 | `predictive_pass: bool` | `predictive_status: str` (3값) + `top_n · bottom_n` 노출 (사용자 진단용) |
| UI `VerificationBucketTable` confidence 표 | pass/fail 만 표시 | insufficient_n → "표본 부족 (n=X/30)" 회색 · fail → "예측력 없음 · 컬럼 삭제 대기" 노란 · pass → "예측력 확인 (top-bottom Y%p)" 초록 |

### D3. CI 순서 강제 실효화 · (b) 채택

**Fable 5 지적 (원문)**:
> "`.step_a_gate_ok` 는 배포된 서버에서 `step_a_gate_check.py` 가 생성하는 파일인데 확인 주체는 `.github/workflows/deploy.yml` 의 job — GitHub Actions 러너는 서버 파일시스템을 볼 수 없음. 문장을 러너 접근 불가능한 파일로 바꿨을 뿐. 해법 셋 중 하나: (a) 커밋 (b) CI 에서 SSH/API로 서버 /verification 조회 (c) health 엔드포인트 step_a_passed."

**사용자 선택**: **(b) CI 에서 `curl /verification` 조회** · SSH 불필요 · 위조 마찰 큼.

**구체 변경**:

| 위치 | v4 | v5 |
|---|---|---|
| `backend/scripts/step_a_gate_check.py` | 서버 로컬 marker `.step_a_gate_ok` 생성 | **삭제** (서버 로컬 marker 폐기) |
| `.github/workflows/deploy.yml` | (v4 · marker 존재 확인 job · 러너 접근 불가) | **신규 job `serenity_hunter_step_gate`**:<br>trigger · Step B/C whitelist 경로 (`backend/api/routes/serenity_hunter.py` · `frontend/app/influencer/serenity-hunter/**`) 변경 감지 시<br>실행 · `curl -sf https://optimus8.cafe24.com/api/v1/serenity/verification` 후 `jq -e '.hero.gate_events_have >= 50 and .hero.gate_open'` · 실패 시 CI fail<br>덧붙임 · Step C 는 `SERENITY_HUNTER_STEP_C_APPROVED=true` env 도 확인 (사용자 수동 승인 · 기존 v4 조항 유지) |
| Verification 방법 §2.12 Step A 완료 5번 | `python backend/scripts/step_a_gate_check.py` 통과 · `.step_a_gate_ok` marker | **삭제** · 대신 `curl https://optimus8.cafe24.com/api/v1/serenity/verification | jq '.hero.gate_events_have, .hero.gate_open'` 로 GitHub Actions job 이 자동 검증 |

**동작 흐름**:
1. Step A 배포 → 서버 크론 매일 새벽 backtest·benchmark 갱신 → `/verification` `hero.gate_events_have >= 50` 자연 도달
2. Step B 코드 커밋 → deploy.yml 이 whitelist 감지 → `serenity_hunter_step_gate` job → curl 실패 시 배포 중단
3. Step B 정상 배포 후 사용자 브라우저 검토 → `SERENITY_HUNTER_STEP_C_APPROVED=true` env 설정
4. Step C 코드 커밋 → 같은 job + env 확인 → 배포
